# PRD - 药按时 MVP

## 1. 文档定位

- 文档名称：药按时 MVP 产品需求文档
- 文档路径：`Standard document/PRD.md`
- 文档用途：作为后续产品、设计、前端、后端、测试的唯一正式需求基线
- 参考来源：仓库 `docs/` 目录仅作历史参考，不作为当前开发权威标准

## 2. 产品概述

### 2.1 产品名称

药按时

### 2.2 产品目标

面向卒中随访及慢病用药管理试点场景，提供一个可推广、可落地、可量化的用药管理系统。MVP 阶段先完成最小闭环：

1. 患者按时服药与打卡
2. 药师跟进异常与提供干预
3. 必要时升级医生处理
4. 对依从性、满意度、知识测评和卒中风险进行量化

### 2.3 目标用户

- 患者：慢病患者，首期以卒中随访患者为主
- 亲情号：患者家属或陪护，可协助提醒、打卡、提交工单
- 药师：负责建档、维护用药计划、处理工单、干预随访
- 医生：仅处理被药师升级的问题

### 2.4 终端形态

- 患者端：Android App
- 药师端：Web
- 医生端：Web

## 3. 背景与问题

当前患者长期用药存在以下问题：

1. 患者依从性差，容易漏服、错服、延迟服药
2. 老年患者智能机操作能力弱，首录后难以持续复用
3. 患者不愿填写复杂表单，录入负担过重
4. 药师缺少结构化工具来持续跟踪、提醒、干预和量化服务效果
5. 医患药协作链条不清晰，问题升级路径不稳定

因此，MVP 要优先解决：

1. 低负担录入
2. 固定药师服务闭环
3. 工单协作与升级链路
4. 用药依从性与服务效果量化

## 4. 产品范围

### 4.1 MVP 范围内

1. 患者手机号验证码登录
2. 患者绑定院内患者身份
3. 药师创建和维护用药计划
4. 患者按提醒完成服药打卡
5. 漏服后 24 小时内补录或更正
6. 亲情号绑定与代打卡、代提工单
7. 患者提交工单，药师处理，必要时升级医生
8. 处方拍照上传，药师 OCR 后确认入库
9. 高风险药物相互作用规则提醒
10. 依从性统计与 Excel/CSV 导出
11. 10 题慢病知识测评
12. 工单关闭后满意度评分
13. ABCD2 风险评分计算
14. Web 端站内提醒、声音提醒、WebSocket 推送

### 4.2 明确不在 MVP 范围内

1. 互联网开方
2. 在线支付
3. 药品配送
4. 医保结算
5. iOS 版本
6. AI 诊断、AI 开药、AI 替代药师/医生决策
7. 大而全内容运营系统
8. 复杂审核型服药打卡证据流

## 5. 核心成功标准

### 5.1 业务成功标准

1. 患者能够独立或在亲情号协助下完成提醒查看、服药打卡、工单提交
2. 药师能够完成建档、计划维护、异常干预、工单处理、升级医生
3. 医生能够只处理升级工单并回写结论
4. 系统可输出依从性、满意度、知识测评、ABCD2 风险评分结果

### 5.2 试点成功标准

- 试点范围：单社区或单团队
- 试点人群：30-50 名卒中随访患者
- 试点周期：4 周
- 验收口径：核心链路稳定，无高风险误导，无高频漏提醒，指标有正向变化趋势

## 6. 用户角色与权限

### 6.1 患者

- 可登录、绑定、查看提醒、打卡、查看历史、提交工单、查看工单结果
- 只读自己的用药计划
- 不可自行编辑正式用药计划

### 6.2 亲情号

- 独立账号，手机号验证码登录
- 每名患者最多绑定 2 个亲情号
- 可代打卡、代提交工单
- 可查看完整照护视图
- 不可查看药师内部备注
- 被解绑后立即失去权限，但历史记录保留

### 6.3 药师

- 固定责任药师负责患者
- 可建档、补全患者资料、维护用药计划、处理工单、进行 DDI 确认、导出报表
- 必要时可升级医生

### 6.4 医生

- 仅查看并处理被升级给医生的工单
- 不参与全量患者浏览

## 7. 核心业务流程

### 7.1 入组绑定流程

1. 药师在线下与患者面对面完成入组
2. 药师确认患者身份，建立或绑定院内患者 ID
3. 患者使用手机号验证码登录 App
4. 完成绑定后即可进入主功能
5. 实名与问卷不作为主功能阻塞门槛

### 7.2 用药执行流程

1. 药师创建或维护患者用药计划
2. 系统生成提醒任务
3. 患者或亲情号按提醒执行打卡
4. 系统记录依从性结果并更新统计
5. 若漏服或异常，可补录或提交工单

### 7.3 工单协作流程

1. 患者或亲情号提交工单
2. 工单通知责任药师
3. 药师处理，必要时升级医生
4. 医生处理并回写结论
5. 当前处理人直接关闭工单
6. 工单关闭后可触发满意度评分

## 8. 工单状态机

MVP 工单状态固定为 5 态：

1. 已提交
2. 药师处理中
3. 待医生
4. 医生处理中
5. 已完成 / 已驳回

补充规则：

- 药师和医生都可以对当前处理中的工单执行驳回
- 驳回必须填写原因
- 非工作时段允许提交工单，但提示将在工作时段处理
- 急症场景不走线上处理闭环，系统直接提示线下急诊并标红

## 9. 功能需求

### 9.1 登录与会话

#### 描述

- 患者和亲情号通过手机号 + 验证码登录
- 会话模型采用 `Access Token + Refresh Token`

#### 验收标准

1. 登录成功后进入已绑定用户首页
2. 未绑定用户进入绑定流程
3. 会话失效后可通过刷新机制续期
4. 登录失败时给出明确错误提示，并支持重试

### 9.2 患者绑定

#### 描述

- 患者身份唯一键为“手机号 + 院内患者 ID”
- 首次绑定需要药师确认
- 重复患者合并由药师确认

#### 验收标准

1. 成功绑定后可进入主功能
2. 未完成绑定的用户不可进入用药主链路
3. 绑定失败要给出明确原因

### 9.3 患者首页

#### 描述

首页优先展示：

1. 今日待服药事项
2. 下一次提醒时间
3. 最近打卡结果
4. 工单入口

#### 验收标准

1. 首页打开后 1 屏可看到今日核心任务
2. 患者不需要多层跳转才能完成打卡

### 9.4 用药计划

#### 描述

- 用药计划由药师创建和维护
- 患者只读
- 药师修改后，当天尚未发生的提醒立即重算
- 已发生的历史记录不回改

#### 验收标准

1. 药师可新增、编辑、停用计划
2. 患者端可看到最新生效计划
3. 同步后新提醒时间正确

### 9.5 服药打卡

#### 描述

- 首版采用极简打卡模型
- 每条记录至少包含：时间、药品、剂量、结果、备注
- 结果包含：按时、延迟、漏服、跳过
- 跳过原因可选
- 24 小时内允许更正
- 若患者与亲情号重复提交，同一剂次以 24 小时内最后一次为准，保留审计

#### 验收标准

1. 患者可在提醒后快速完成打卡
2. 更正后历史轨迹可追踪
3. 不支持硬删除记录

### 9.6 提醒与通知

#### 描述

- 患者端通过本地提醒 + App 内提醒工作
- 离线时支持本地缓存，联网后自动同步
- 药师/医生 Web 端使用 WebSocket + 站内弹窗 + 声音提醒

#### 验收标准

1. 患者能收到待服药提醒
2. 药师收到新工单提醒
3. WebSocket 不可用时，系统仍可降级为站内提示

### 9.7 亲情号

#### 描述

- 每名患者最多 2 个亲情号
- 患者一次性授权后绑定
- 亲情号可代打卡、代提工单

#### 验收标准

1. 亲情号登录后可看到患者照护视图
2. 解绑后立即不能继续代操作
3. 历史代操作记录仍保留

### 9.8 工单管理

#### 描述

患者工单固定类型为：

1. 用药咨询
2. 漏服/错服
3. 不良反应
4. 计划变更
5. 其他

附件范围首版仅支持图片。

#### 验收标准

1. 患者可提交文本 + 图片工单
2. 药师能接收、处理、升级、驳回、关闭
3. 医生仅处理升级工单

### 9.9 OCR 处方录入

#### 描述

- 患者可上传处方照片
- 首版以电子/打印处方为主
- OCR 结果仅结构化药品明细：药名、剂量、频次、用法
- 置信度低或识别失败时，药师手工录入标准模板

#### 验收标准

1. 药师可查看原图并确认结果
2. 识别失败不阻塞入库
3. 最终入库结果以药师确认版本为准

### 9.10 药物相互作用 DDI

#### 描述

- 首版使用规则库进行高风险组合提醒
- 采取“强提醒 + 药师确认”策略
- 不直接阻断保存

#### 验收标准

1. 命中高风险组合时必须提示
2. 药师确认后才可继续保存
3. 保留确认操作记录

### 9.11 量化与评估

#### 描述

- 依从性指标：按时服药率 = 按时次数 / 应服次数
- 知识测评：10 题固定单选题，首日和第 4 周各一次
- 满意度：工单关闭后 5 分制评分
- 疾病风险：MVP 先支持 ABCD2

#### 验收标准

1. 可查看 7 天与 30 天依从性
2. 药师可导出 Excel/CSV 报表
3. 知识测评纳入试点任务，但不阻塞主链路
4. 满意度不阻塞工单关闭
5. 药师更新关键字段后，ABCD2 自动重算

## 10. 用户故事

### 10.1 患者

- 作为患者，我希望登录后直接看到今天要吃的药，这样我不用自己查找。
- 作为患者，我希望点几下就能完成打卡，这样我愿意长期使用。
- 作为患者，我希望漏服后还能补录，这样我的记录更真实。
- 作为患者，我希望有问题时能快速提交工单给药师。

### 10.2 亲情号

- 作为家属，我希望能帮老人代打卡和提交问题，这样老人不会因为不会操作而中断使用。

### 10.3 药师

- 作为药师，我希望患者基础信息尽量少填，由我补全医学信息，这样不会因为录入负担导致流失。
- 作为药师，我希望能直接看到异常依从性和新工单，这样我能及时干预。
- 作为药师，我希望处方能通过 OCR 辅助录入，这样减少重复输入。

### 10.4 医生

- 作为医生，我希望只接收已经被药师筛选后的升级问题，这样我只处理真正需要医生介入的事项。

## 11. 非功能需求

### 11.1 可用性

1. 患者端操作需尽量一步一屏
2. 老年用户优先，界面需适配大字和清晰提示
3. 核心功能必须支持手机使用

### 11.2 数据与合规

1. 打卡、工单、计划变更、升级决策必须保留审计日志
2. 药师/医生 Web 端需对手机号、身份证等敏感信息脱敏展示
3. 数据至少保留 12 个月

### 11.3 服务时效

1. 服务时间：工作日 08:30-17:30
2. 药师首响 SLA：工作时间内 2 小时
3. 医生首响 SLA：工作时间内 4 小时

## 12. 关键数据项

### 12.1 患者最小必填信息

1. 姓名
2. 年龄
3. 手机号
4. 当前用药

### 12.2 服药记录核心字段

1. 患者 ID
2. 计划项 ID
3. 计划时间
4. 实际时间
5. 药品名称
6. 剂量
7. 结果
8. 备注
9. 操作人类型
10. 是否补录

### 12.3 工单核心字段

1. 工单类型
2. 标题
3. 描述
4. 附件图片
5. 当前状态
6. 当前处理人
7. 升级记录
8. 驳回原因
9. 满意度评分

## 13. 约束与默认规则

1. 患者正式接口入口统一为 `/app-api/**`
2. 药师/医生管理接口统一为 `/admin-api/**`
3. 患者主功能必须登录
4. 绑定和药计划是进入主功能的前置条件
5. 非 MVP 菜单在试点角色下全部隐藏
6. 固定责任药师缺席时允许管理员改派
7. `docs/` 中 legacy 契约若与本 PRD 冲突，以本 PRD 为准

## 14. 里程碑

### 14.1 P0

1. 表单瘦身
2. 药师补全与同步
3. 处方拍照 OCR 闭环
4. 亲情号
5. 工单通知闭环
6. 依从性报表

### 14.2 P2

1. 科普内容库与推送
2. 内容运营能力
3. 更复杂的扩病种策略

## 15. 验收清单

上线试点前必须验证以下主链路：

1. 登录/绑定 -> 首页 -> 提醒 -> 打卡
2. 漏服 -> 24 小时内补录/更正
3. 提交工单 -> 药师处理 -> 升级医生 -> 回写 -> 关闭
4. 处方拍照 -> OCR -> 药师确认入库
5. 依从性、知识测评、满意度、ABCD2 均可出结果
